1. 现状与差距

xsolve 当前没有任何账号体系。每个浏览器拿到的是一个匿名会话：模式（学生 / 家长）只是前端 localStorage 里的一个开关，任何人都能自由切换；所有数据（会话、答题流水、掌握度、画像）都挂在全局单例 student_id = 'me' 上。这套「单人单机」假设在只有自家人使用时没问题，但一旦想让多个孩子、或家长与孩子分别登录，就完全站不住脚。

现有能力实现位置问题
模式切换 student / parentfrontend/js/state.js（localStorage.ai_mode）+ backend/session.js:createSession纯前端开关，学生可自行切到家长模式拿到讲解与答案，约束形同虚设
会话归属chat_sessions.role、chat_turns.rolerole 只记「模式」，不记「是谁」。无法区分不同孩子/家长的会话
学生记忆隔离键student_id 硬编码 'me'（db.js、turnController.autoLogAttempts、mcp-tools.js）所有学生的答题流水 / 掌握度 / 画像 / 记忆事实混在同一行空间，无法多用户
会话本地持久化键frontend/js/state.js（xsolve_session_<mode>）键只按模式分，不按账号分，多账号同机使用会串会话
管理页（评估 / Prompt / 模型配置 / 学习档案）backend/app.js 直接暴露 /api/eval/*、/api/prompts/*、/api/settings/*、/api/memory/*零鉴权，任何能访问服务的人都能改模型 Key、改 Prompt、看他人学习档案
后端依赖package.json：express / better-sqlite3 / zod / claude-agent-sdk无任何鉴权 / 密码库——本方案尽量不出新增原生依赖
一句话总结差距

系统缺的是一层「身份」：谁在登录、他是什么角色、他能看谁的数据。补上这层身份后，「家长看孩子」「学生不许拿答案」「记忆按孩子隔离」都会自然成立——因为记忆系统在 P0 时已经预留了 student_id 列，只差把 'me' 换成真实用户 id。

2. 设计目标与原则

设计目标

账号 + 登录：学生与家长各自拥有账号，用户名 + 密码登录。

会话鉴权：登录态用服务端会话（httpOnly Cookie），业务与管理 API 全部经过鉴权中间件。

角色区分：区分学生 / 家长，家长可绑定并查看自己的孩子；学生的数据只属于自己。

顺水推舟：最大化复用现有结构——把 student_id='me' 换成真实 id，不推倒记忆系统重来。

2.1 设计原则

  • 零新增原生依赖：密码哈希用 Node 内置 crypto.scrypt，会话令牌用 crypto.randomBytes——不引入 bcrypt / jsonwebtoken 这类需要编译或不必要的库。
  • 服务端会话而非 JWT：家庭场景、单体服务、需要「登出即时失效」，服务端会话表最直接。JWT 反而要额外处理吊销。
  • 兼容现网数据：现有 xsolve.db 里的历史会话与记忆，通过一个「引导账号」承接，防御式迁移（SELECT col LIMIT 0 探测 → ALTER TABLE ADD COLUMN）。
  • 最小权限：学生账号锁定学生模式；管理页仅「家庭管理员」可见；家长只能访问已绑定的孩子。
  • 后端为最终防线：前端显隐只是体验，所有权限判定必须在后端中间件里再判一次。

3. 核心模型：厘清两个「角色」

这是本方案最容易被搞混、也最需要先说清楚的一点：系统里存在两个层次的「角色」，二者不是一回事。

概念取值存在哪含义 / 决定什么
账号角色 account rolestudent / parent / adminusers.role这个登录「人」是谁。决定他能访问哪些 API、能创建什么模式的会话、能看谁的数据
会话模式 session modestudent / parentchat_sessions.role（沿用旧列名= mode）这条对话用哪套系统提示词：学生版（不给答案）还是家长版（可讲解）。由账号角色派生，不自由选择

映射规则简单而确定：

  • 学生账号 → 只能创建 student 模式会话；session.student_id = 自己（答题流水记在自己名下）。
  • 家长账号 → 只能创建 parent 模式会话；session.student_id = 选中的已绑定孩子（家长陪孩子做题时，孩子的答题流水仍记在孩子名下）。
  • admin 账号 → 可进管理页；一般不出现在日常辅导界面。
为什么这样拆

把「账号角色」和「会话模式」分开后，现有 prompt_versions.role（student/parent 两套提示词）完全不用动——选哪套提示词仍由会话模式决定，只是模式不再由前端开关随便挑，而是由登录账号的角色强制派生。这恰好复用了你已经在用的机制。

3.1 分层架构

请求自上而下穿过四层：浏览器持 httpOnly Cookie → Express 鉴权中间件解析会话与角色 → 业务 Controller 按归属读写 → SQLite 按 student_id 隔离数据。

3.2 鉴权分层（权限矩阵）

不同 API 组要求不同的身份与角色。✅ = 允许，🚫 = 拒绝（403），🔒 = 仅限本人的数据。

API 组未登录学生家长admin
/api/auth/login·register✅✅✅✅
/api/auth/me·logout🚫🔒🔒🔒
/api/session/*、/api/session/:id/turn（对话）🚫(401)🔒 自己的会话🔒 自己的会话✅
/api/memory/*（学习档案）🚫🔒 自己🔒 已绑定孩子✅
/api/children（孩子列表）🚫🚫✅✅
/api/prompts/*、/api/settings/*、/api/eval/*🚫🚫✅ 仅管理员家长✅

4. 数据模型

在现有 xsolve.db 中新增 4 张表（users / user_sessions / family_links / invite_codes），并给 chat_sessions 补两列归属字段。记忆相关的 4 张表（student_attempts 等）结构不变，只是 student_id 从常量 'me' 变成真实用户 id。

4.1 新表 DDL

-- users：账号 CREATE TABLE IF NOT EXISTS users ( id TEXT PRIMARY KEY, -- uuid role TEXT NOT NULL, -- 'student' | 'parent' | 'admin' username TEXT NOT NULL UNIQUE, -- 登录名 display_name TEXT, -- 显示名（如"小明"） password_hash TEXT NOT NULL, -- scrypt 输出：salt$hash（hex） is_admin INTEGER NOT NULL DEFAULT 0, -- 家庭管理员：可进管理页 status TEXT NOT NULL DEFAULT 'active', created_at INTEGER NOT NULL DEFAULT (strftime('%s','now')), last_login_at INTEGER ); -- user_sessions：登录态（cookie token → user） CREATE TABLE IF NOT EXISTS user_sessions ( token TEXT PRIMARY KEY, -- randomBytes(32).hex user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE, created_at INTEGER NOT NULL DEFAULT (strftime('%s','now')), expires_at INTEGER NOT NULL, user_agent TEXT, ip TEXT ); CREATE INDEX IF NOT EXISTS idx_user_sessions_user ON user_sessions(user_id); -- family_links：家长-孩子绑定（多对多） CREATE TABLE IF NOT EXISTS family_links ( parent_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE, student_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE, relation TEXT, -- '父' / '母' / '监护人' created_at INTEGER NOT NULL DEFAULT (strftime('%s','now')), PRIMARY KEY (parent_id, student_id) ); -- invite_codes：家长生成邀请码，孩子注册时凭码自动绑定 CREATE TABLE IF NOT EXISTS invite_codes ( code TEXT PRIMARY KEY, parent_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE, expires_at INTEGER, used_by TEXT, created_at INTEGER NOT NULL DEFAULT (strftime('%s','now')) );

4.2 既有表迁移（防御式）

-- chat_sessions 增加归属列（沿用 db.js 现有探测式迁移写法） try { db.prepare("SELECT user_id FROM chat_sessions LIMIT 0").get(); } catch { db.exec("ALTER TABLE chat_sessions ADD COLUMN user_id TEXT"); } try { db.prepare("SELECT student_id FROM chat_sessions LIMIT 0").get(); } catch { db.exec("ALTER TABLE chat_sessions ADD COLUMN student_id TEXT"); }
历史数据承接

现网 xsolve.db 已有匿名历史。迁移策略：首次启动若无任何用户，自动创建一个引导学生账号（如 demo / demo123，可改），并把现存所有 student_id='me' 的记忆行、以及 chat_sessions 中 user_id IS NULL 的旧会话，统一改挂到该账号 id 上。这样老数据不丢，登录后即可看到。

5.3 模式与会话归属的派生逻辑

在 createSession() 入口处，按登录账号角色强制决定 mode 与 student_id，忽略前端传来的自由值：

// backend/session.js —— 由账号角色派生，而非信任前端 body.mode function deriveSessionScope(user, body) { if (user.role === 'student') { return { mode: 'student', student_id: user.id }; // 学生锁死学生模式 } if (user.role === 'parent') { const sid = body.studentId; assert(isBoundChild(user.id, sid)); // 必须是自己绑定的孩子 return { mode: 'parent', student_id: sid }; } return { mode: body.mode || 'parent', student_id: body.studentId || null }; // admin }

家长陪孩子做题时，对话走家长版提示词（mode='parent'），但孩子的答题流水仍记在孩子名下（student_id=孩子id）——这正是「谁在用」与「数据属于谁」解耦的价值。

7. Prompt 与配置改动

Prompt：基本无需改动

学生的「不给答案」约束本就写在 SYSTEM_PROMPT_STUDENT（config.js），家长版在 SYSTEM_PROMPT_PARENT；活跃版本存在 DB prompt_versions。本方案不改提示词内容——只是让「学生账号拿不到家长版」这件事由后端强制保证，提示词与模式绑定的机制原样复用。

唯一可选微调：记忆摘要注入段的措辞从「这位学生」保持中性即可，无需因多用户而改。

⚠️ 改 prompt ≠ 改 config.js（项目铁律）

若确实需要改动 config.js 里的提示词，务必要同步写入 DB 并激活（跑 backend/scripts/upgrade-*.mjs 或在 /prompts.html 激活新版本），否则线上仍走 DB 里的旧版本。本方案不改 prompt，故无同步动作。

8. 前端改动

  • 登录页 frontend/login.html：用户名 + 密码；注册区按角色分叉（家长可「生成邀请码」，学生填「邀请码」绑定家长）。
  • 统一鉴权包装 frontend/js/auth.js：所有 fetch 走 credentials:'include'；集中处理 401 → 跳登录、403 → 提示无权限；提供 getMe() 供各页渲染账户信息。
  • 主界面按角色裁剪 index.html + state.js：
    • 学生账号：隐藏模式切换与「家长模式」入口；顶栏只留题目的日常操作。
    • 家长账号：「我的孩子」下拉（切换查看对象）；保留管理入口（若为管理员家长）。
    • 会话本地键加入账号前缀，切换账号不串会话。
  • 管理页收口：eval.html / prompts.html / settings.html / student-memory.html 非管理员隐藏入口，后端中间件兜底 403。

9. 里程碑与验收

P0 · 身份与隔离

可用最小闭环

  • users/user_sessions 表 + 迁移
  • 注册 / 登录 / 登出 / me
  • httpOnly Cookie 会话 + requireAuth
  • 业务 API 全覆盖鉴权中间件
  • 会话与记忆按 user 隔离（'me' → 真实 id）
  • 登录页 + 401 跳转
  • 学生账号锁定 student 模式
  • 历史数据迁移到引导账号
P1 · 家长与孩子

家庭关系

  • family_links + invite_codes
  • 邀请码绑定流程
  • 家长查看孩子会话列表
  • 家长查看孩子学习档案（只读）
  • requireAdmin 锁管理页
  • 家长端「我的孩子」切换
P2 · 完备性

运营与安全

  • 修改密码 / 密码重置
  • 一个学生多家长绑定
  • 登录限流与审计日志
  • 游客试用模式（可选）
  • 管理页：账号管理界面
验收标准

Definition of Done

  • 未登录访问业务 API → 401
  • 学生访问管理 API → 403
  • 家长访问非绑定孩子档案 → 403
  • 两个学生账号记忆互不串
  • 登出后旧 Cookie 立即失效
  • 历史会话登录后可见

10. 开放问题

  • 游客 / 试用：是否允许不登录先试？若允许，试用的数据是否落库、落给谁？（倾向：P0 直接要求登录，避免游离子空间，简化归属。）
  • 家长 = 家庭管理员？：本方案默认「家长可被标记为 is_admin」以进管理页；也可改成独立的全局 admin，与家长解耦。取决于你希望谁能改模型 Key / Prompt。
  • 学生能否自主注册：家长邀请码 ALLOW_SELF_REGISTER_STUDENT=false 是更安全默认，但会增加家长操作成本。
  • 多家长绑定同一孩子：family_links 主键是 (parent_id, student_id)，天然支持一个孩子被爸妈同时绑定；是否需要「主监护人」概念待定。
  • 更远：手机号 / 微信 / SSO 登录？——家庭场景不必，列为未来选项。
  • 历史数据归属：引导账号 demo 是临时承接方案，是否需要一次性「认领」流程把历史划给真实账号。
