一、背景与目标

xsolve 目前是一个面向小学生的 AI 做题助手 Web 应用：页面分「题目展示 / 做题区（手写草稿）/ AI 交互」三区，已具备 KaTeX 公式渲染、canvas 手写、jsxgraph 交互绘图、语音输入、拍照上传与 SSE 流式对话。

本方案要回答一个问题：如何增加一个手机 App 端，让小学生在手机 / 平板上做题并与 AI 交互。目标形态按优先级递进：先「可安装」（PWA），后「原生」（按需）。

本方案的立场

不追求一步到位的原生 App。先用最低成本把现有能力送到孩子手机上验证，把工程预算优先投在真正决定能否上线的两件事——后端公网化与账号体系，而非重写 UI。

二、现状与关键约束（决定性事实）

xsolve 是典型的「重后端 + 轻前端」结构：AI 能力全部在后端（Express + Claude Agent SDK + SQLite + MCP 工具 + SSE），前端只是一层 HTML/JS。这决定了 App 的形态。

2.1 不可绕过的硬约束

约束事实对 App 端的影响
SDK 原生二进制 @anthropic-ai/claude-agent-sdk 运行时会 spawn 平台专用二进制（如 claude-agent-sdk-linux-arm64/claude） 手机端✗跑不动，必须在 Linux 服务器上跑
原生模块 better-sqlite3 按 Node ABI 编译（本机是 Node 26 / ABI 147） 后端只能在匹配的 Node + Linux 环境运行
无鉴权 现有 40+ 个路由全部零鉴权，chat_sessions 无 owner 字段，settings（含 API Key）全局共享 一上公网即「谁都能用你的额度、看同一个库」✗
CDN 依赖 前端从 jsdelivr 加载 KaTeX / marked PWA 离线需本地化，否则离线白屏
容器 root 限制 Claude Code CLI 拒绝 root 用 bypassPermissions，需 IS_SANDBOX=1（已修复） 部署时保持该环境变量

一句话结论

选型的真正难点不在「App 怎么写」，而在下面那层要从 Mac 上的 localhost 变成一台公网服务器，并补上它现在完全没有的账号体系。

三、选型结论

由于 AI 全在后端，App 只是瘦客户端。四个候选方案的对比（就本项目而言）：

方案复用现有代码上手成本手写/相机/语音分发本项目适配
PWA / 增强 Web ~100% 极低 相机✓ 手写✓；语音受限 加主屏，不进商店 ★★★★★
Capacitor 混合壳 ~95% 低 全部原生能力（插件） 正式上架 iOS/安卓 ★★★★★
React Native / Expo 0（重写） 中高 原生，但 KaTeX/画布要重做 上架 ★★☆
Flutter 0（重写） 高 自绘最强（手写/几何） 上架 ★★★

结论

本项目前端已有 KaTeX、canvas 手写、jsxgraph（iframe）、语音、SSE 且做了双端适配。Capacitor / PWA 都能几乎照搬这套代码；而 RN / Flutter 需要把公式渲染与交互绘图全部推倒重做，投入产出比差。

结合已确认的方向——分发走 PWA、前端暂不重写——最终路线为：

  • Phase 1：现有 Web 升级为可安装 PWA（不重写）。
  • Phase 2：后端公网化 + 账号体系（无论哪种客户端都必做）。
  • Phase 3：按需演进——要么 Capacitor 套壳拿原生能力，要么重写前端。

4.1 通信契约（现有，App 直接复用）

  • POST /api/session 建会话；POST /api/session/:id/turn 发消息（SSE 流式返回）。
  • GET /api/session/:id/history 拉历史；POST /api/session/:id/scratch-image 同步手写草稿图。
  • 校验 / 设置：/api/settings（API Key 等，Phase 2 后需管理员权限）。

SSE 鉴权的坑

浏览器原生 EventSource 不能自定义请求头。当前 /turn 用的是 fetch + 流读取（可控），但若改用 EventSource，鉴权只能走 Cookie 或 URL 携带短时 token。方案见 §6.4。

五、Phase 1：PWA 化（1–2 天）

目标：在不重写前端的前提下，让现有 Web 可安装到手机主屏、离线可用、全屏运行。

  GET /api/problems 等只读接口   → Stale-While-Revalidate（可选）

5.3 PWA 的能力天花板（提前知道）

  • iOS 上 Web Push 受限（16.4+ 才部分支持），Android 支持较好。
  • 无后台常驻、不能上架商店、无系统级深链 / 分享。
  • 手写用 canvas + Pointer Events（可拿压感）够用；但极致笔迹延迟与防手掌误触需原生能力——这正是 Phase 3 的触发条件之一。

5.4 验收标准

  • 手机浏览器打开后可「添加到主屏」，图标/名称/主题色正确。
  • 断网后可加载应用外壳并显示明确提示（不白屏）。
  • 全屏运行无地址栏；三区布局在手机竖屏可用，手写/公式不溢出。

六、Phase 2：后端公网化 + 认证与多用户隔离

这是本方案的重心，也是与客户端选型无关、必须完成的工程。

  • 容器内保持 IS_SANDBOX=1（否则 SDK 在 root 下直接退出）。

6.2 认证方案选型

方案复杂度适合度说明
Session Cookie（服务端会话） 低 ★★★★★ 同源部署天然友好；Cookie 自动随请求发送，SSE 鉴权最省事；需 CSRF 防护
JWT（Bearer） 中 ★★★★ 无状态、易扩展；但 EventSource 带不了 header，需额外处理
第三方登录（微信/手机号） 中高 ★★★★ 家长用户最顺手；但需资质与回调配置，可后置

建议

起步用服务端 Session Cookie（自建账号，邮箱/用户名 + 密码哈希），快速打通且 SSE 友好；后续再接微信/手机号登录。密码用 argon2 / bcrypt 哈希，绝不明文。

6.3 数据模型变更

需要新增 users 表，并给现有表加归属字段（用防御性迁移，参考 backend/scripts/backfill-prompt-version.mjs 的写法）：

-- 新增用户表
CREATE TABLE users (
  id TEXT PRIMARY KEY,
  username TEXT UNIQUE NOT NULL,
  password_hash TEXT NOT NULL,
  display_name TEXT,
  role TEXT NOT NULL DEFAULT 'parent',   -- parent | student | admin
  created_at INTEGER NOT NULL DEFAULT (strftime('%s','now'))
);

-- 会话归属（迁移：ALTER TABLE ... ADD COLUMN，容忍已有数据）
ALTER TABLE chat_sessions ADD COLUMN user_id TEXT;   -- 归属家长/账号
ALTER TABLE chat_sessions ADD COLUMN student_id TEXT;-- 可选：孩子档案

-- settings 归属：全局配置仅 admin 可改；模型 Key 收归管理员
ALTER TABLE settings ADD COLUMN scope TEXT NOT NULL DEFAULT 'global';

迁移注意

已有 chat_sessions 数据无 owner。迁移时将其归属到一个「迁移前」默认账号（或管理员），避免历史数据对所有人可见。

6.4 鉴权落地要点

  • 中间件：在 backend/app.js 的 createApp() 里、路由注册之前，加全局鉴权中间件，仅放行 /healthz、/api/auth/*、静态资源。
  • 越权防护：所有 /api/session/:id/* 必须校验 session.user_id === 当前登录用户，否则 403（防止拿到别人 session id 就乱读）。
  • SSE 鉴权：/turn 走 Cookie 鉴权最稳；若用 Bearer，则签一个短时一次性 token 拼在 URL（?token=...），服务端校验后立即失效。
  • 管理面收口：/api/settings（API Key）、/api/prompts 仅 admin 可访问；否则任何家长都能改你的模型 Key。

6.5 Agent SDK 并发与资源

这是最容易翻车的地方

每个会话会 spawn 一个 Claude Code 原生进程，内存占用可观。单机裸跑在并发上来后极易 OOM（与之前 npm ci 被 137 杀掉同一类问题）。

  • 并发上限 + 排队：全局信号量限制同时活跃的 SDK 会话数，超出则排队并给前端「排队中」的流式提示。
  • 空闲回收：会话空闲 N 分钟后 destroySession，释放子进程。
  • 规模化（用户变多后再做）：拆分「会话调度器 + 无状态 worker」，或每用户独立容器池化。
  • 限流：按用户限制「每分钟 turn 数 / 每日 token 量」，防止额度被滥用。

6.6 安全清单

项措施
CORS / 来源同源部署无需放开 CORS；若 Capacitor 用 capacitor://localhost，需精确白名单，禁止 *
密钥保护API Key 仅存服务端 + 仅 admin 可改；日志脱敏（settings 回显已做掩码）
请求体大小现有 express.json({ limit: '50mb' }) 偏大，按需收紧（草稿图除外）

传输强制 HTTPS（HSTS），HTTP 301 跳转

6.7 验收标准

  • 未登录访问任意 /api/* 均被拒（401），/healthz 除外。
  • 用户 A 无法读取/操作 用户 B 的 session（403）。
  • 非 admin 访问 /api/settings 返回 403；admin 正常。
  • 并发压测下无 OOM，超出并发上限时前端能收到「排队」提示。

七、Phase 3：演进到原生（Capacitor 预案）

7.1 触发条件（满足其一即考虑）

  • 需要上架应用商店（PWA 做不到）。
  • 需要 推送 / 后台任务 / 系统深链。
  • 手写需要极致延迟与防手掌误触（Apple Pencil / 安卓手写笔原生能力）。

7.2 迁移路径

  1. Capacitor 套壳：把现有 frontend/ 直接作为 Web 资源打进原生工程，代码几乎不动。
  2. 插件桥接：需要原生能力时按需引入/自写 Capacitor 插件（相机、文件、推送、手写笔）。
  3. 若坚持重写（当年选了 Flutter/RN）：注意 jsxgraph 交互绘图与 KaTeX 公式仍需 WebView 承载，纯原生重写成本高——这也是当初不首选重写的原因。

十一、移动端体验修复实录（已完成）

为什么单列一章

前面十节把移动端放在「先能装到主屏、再考虑公网、最后考虑原生」的排期里，体验细节散在 Phase 1 的验收标准中。实际用下来确认了移动端就是主要使用场景（录题 / 拍题 / 写题），于是单独做了一轮以真机视口为基准的排查。结论是：查出来的两个主要问题都不是「体验不够好」，而是功能实际不可用——而且都只在手机上暴露，桌面浏览器窗口够宽、也不会去点移动端的 Tab，完全看不出来。

11.1 问题一：手写内容会凭空消失（写题）

画布靠改 canvas.width / canvas.height 来适配尺寸，而改这两个属性必然清空位图；代码里却没有任何「按笔画重绘」的逻辑。于是只要触发一次 resize，写到一半的内容就没了。移动端触发得极其频繁：

  • 每次从「题目」切回「做题」都会重设尺寸（switchTab() 里显式调用）；
  • 软键盘弹出 / 收起、旋屏、地址栏收起展开，同样会触发 resize。

同一处还有两条同源问题，一起修了：

问题触发场景后果处理
面板隐藏时量到 0×0，照样设尺寸在 AI Tab 上键盘弹收触发 resize画布被清成 0×0，内容永久丢失加零尺寸守卫 + 尺寸无变化短路
导出草稿用 getBoundingClientRect() 算尺寸在 AI Tab 点「检查过程」（此时「做题」面板是 display:none）导出空图 → AI 看到的草稿是白纸改用画布像素尺寸 canvas.width/height

修法是让笔画成为可重放的真相来源：结构从裸坐标数组改成 { t, p }（带上工具类型，橡皮才能忠实重放），尺寸变化后按笔画重放一次。另外补了「撤销」，并在多指 / 掌托时结束当前笔画，避免拖出乱线。

实测对照

注入两笔后切一次 Tab：修复前墨迹像素 12957 → 0，修复后 12957 → 12957。

11.2 问题二：拍题入口被裁到屏幕外（拍题）

工具栏是 max-height:36px + flex-wrap:nowrap + overflow:hidden（「只显示第一行」），而同一个断点又把按钮抬到 min-height:34px。在 390px 视口下实测各按钮右边界：

按钮右边界可见性
✒️ 画笔 / 🧽 橡皮 / 🗑️ 清空 / 👁️ 识别草稿≤ 287px可见
📷 上传我的解答400px半截露在屏幕外
📖 上传题目488px完全在屏幕外
✏️ 输入题目576px完全在屏幕外

也就是说，移动端最核心的三个动作都藏在「⋯ 更多」二级菜单里。改为单行横向滚动（右缘淡出提示可滑、隐藏滚动条），并把「📷 拍题」升为主色按钮排到第一位；纵向仍然只占一行，把高度留给手写画布。改完 scrollWidth=837 / clientWidth=390，其余项手指一划即达，折叠开关随之删除。

11.3 拆分「拍照」与「从相册选」

原来四个图片入口全部带 capture="environment"。这在 iOS / Android 上的语义是「直接打开相机」——用户没有机会选已有照片：老师微信发来的题目截图、之前拍好的照片，都传不上去。现在拆成四个 input：题目 / 解答 × 拍照（带 capture）/ 相册（不带）。

11.4 新增拍照后裁剪

对着作业本拍一整页，直接整张送 AI 会串题、把邻题当题干。新增 frontend/js/crop.js：

  • Pointer Events 一套代码同时吃触屏与鼠标；整体拖动 + 四角缩放 + 三分线，选择框钳制在图片范围内；

11.7 仍未做的

  1. 证书来源仍是自签 CA（本次未动）。当前「装 CA → 换网失效 → 刷证书致 SPKI 失效」这一整类摩擦的根因不是 PWA，而是「局域网 IP + 自签证书不构成公信信任」。它与 §10.2 第 4 条（是否有可备案的服务器与域名）是同一个决策：只要有一个域名，用 Let's Encrypt 的 DNS-01 挑战就能签发公信证书（只校验一条 DNS TXT 记录，服务器无需公网可达、无需开 80/443，A 记录可直接指向 192.168.0.112）——流量不出局域网、客户端免装 CA、续期只换证书客户端无感知。这是唯一能同时消掉上述三类问题的方案。
  2. 整页多题拆分：一张照片里有 3 道题时，目前只能逐题裁三次。
  3. 草稿离线暂存：断网时草稿只在内存里，刷新即丢（服务端同步依赖在线）。
  4. 压感与手掌误触仍是 PWA 的能力上限——这正是 §7.1 Phase 3 的触发条件之一，当前只做了「多指即结束当前笔画」的粗粒度防误触。
